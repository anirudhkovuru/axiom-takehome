# Architecture and interview notes

## System shape

Axiom Workbench has three logical layers:

1. The **workspace UI** manages navigation, chat composition, streamed progress, and artifact inspection.
2. The **orchestration API** owns chat state, run lifecycle, tool dispatch, and the OpenAI credential.
3. The **analysis runtime** accesses DuckDB read-only and executes controlled Python in a child process.

The local MVP keeps the API and executor in one FastAPI service. Their boundary is still explicit, so execution can move to a remote sandbox later without changing the UI contract.

## What happens when a user sends a message

```text
1. Browser POSTs /api/chats/{chat_id}/messages
2. API commits the user message and a queued run to SQLite
3. API returns the durable run_id immediately
4. Browser opens GET /api/runs/{run_id}/events
5. Worker changes the run to running and begins the agent loop
6. Every plan, step, artifact, and text delta is inserted into run_events
7. The SSE endpoint reads those rows in order and forwards them to the browser
8. Final assistant message is committed and the run becomes completed
9. Browser reloads the canonical chat record from the API
```

The important design choice is **persist before publish**. An event exists in SQLite before it appears in the UI. The UI can therefore reconnect using the SSE event ID and request only events after its last observed ID.

## Streaming

The browser and API use server-sent events rather than WebSockets because the traffic is primarily one-way during a run.

Event types include:

- `run.started`
- `plan.created`
- `step.started`
- `step.completed`
- `step.failed`
- `artifact.created`
- `assistant.delta`
- `run.completed`
- `run.failed`

FastAPI's stream polls the append-only `run_events` table, emits each row with its numeric ID, and sends a heartbeat during quiet periods. Native `EventSource` automatically supplies `Last-Event-ID` on reconnection. Once a terminal run event is delivered, the UI closes the stream and reloads the durable chat.

For the live agent, the backend consumes typed OpenAI Responses API events. Text deltas become `assistant.delta` events. Completed function calls are executed locally; their outputs are appended to the next Responses API request. Tool execution is never performed from partial argument deltas.

### Why SSE instead of WebSockets

- The command is sent once over HTTP and updates flow in one direction.
- Browser reconnection behavior and event IDs are built in.
- SSE is easy to inspect with `curl` and straightforward to proxy.
- WebSockets would be justified later for pause/resume, mid-run user guidance, or collaborative presence.

## Persistence model

SQLite is the source of truth for local application state.

| Record | Purpose |
| --- | --- |
| `chats` | Named conversational workspaces |
| `messages` | Durable user and assistant transcript |
| `runs` | One agent execution per user message |
| `run_events` | Ordered stream and reconnect log |
| `steps` | Inspectable tool executions and status |
| `artifacts` | Metadata and lineage for generated files |
| `experiments` | Named, exportable references to a chat state |

Generated bytes live in `.context/artifacts/{run_id}`. SQLite stores their MIME type, kind, size, path, run, chat, and producing step. This keeps relational queries small while preserving complete lineage.

The browser does not use `localStorage` for product data. Refreshing the page reconstructs the workspace from the API. Only transient rendering state—such as the currently open side panel—lives in React memory.

## Chats versus experiments

A **chat** is mutable working context. It contains questions, answers, runs, steps, and artifacts and can continue to receive follow-up questions.

An **experiment** is a named checkpoint that references a chat and makes it discoverable in the experiment section. Exporting it creates a ZIP containing:

- `report.md` with the transcript
- `manifest.json` with runs, steps, artifact metadata, and timestamps
- SQL and Python source
- CSV/JSON result data
- Generated figures

For this MVP the experiment references the current chat rather than copying every row at save time. A production version would add a revision number or immutable snapshot table so later chat activity cannot change a previously saved experiment's export.

## Agent loop

The live agent uses a small custom Responses API loop:

```text
messages + instructions + tool schemas
                │
                ▼
        model response stream
          │             │
     final text     function calls
                          │
                    execute tools
                          │
                  function outputs
                          └──> next model turn
```

The custom loop is deliberately small. It makes tool boundaries, retries, persistence, and audit behavior obvious during code review. A larger workflow with branching agents or approvals could justify the Agents SDK later.

### Agent tools

- `set_analysis_plan`: publishes a visible plan before data access.
- `inspect_dataset`: searches embedded table and feature documentation.
- `run_sql`: executes one read-only statement and can save CSV output.
- `run_python_analysis`: performs statistics, clustering, or plotting in the controlled worker.

The prompt encodes the interpretation rules supplied with the dataset: ADME QC filtering, clipped versus unclipped values, morphology filtering, transcriptomic significance measures, coverage limits, and non-causal language.

## Analysis runtime and safety

DuckDB connections are opened with `read_only=True`. SQL is also checked to permit one statement beginning with `SELECT`, `WITH`, `SHOW`, `DESCRIBE`, `SUMMARIZE`, or `EXPLAIN`.

Python runs in a separate process with:

- a 45-second timeout;
- a read-only DuckDB connection supplied as `con`;
- a restricted import allowlist;
- blocked filesystem, process, and dynamic-code primitives;
- a run-specific artifact directory;
- captured stdout and generated-file registration.

This is defense in depth for a local take-home, not a hardened hostile-code sandbox. Production execution should run in an ephemeral container or Modal Sandbox with no network, a read-only database mount, CPU/memory limits, and a writable output volume.

## Failure behavior

- A failed tool marks its step failed and records the error.
- The live model receives recoverable tool errors as function outputs and can repair its query or code.
- An unrecoverable run marks `runs.status = failed` and emits `run.failed`.
- Successful earlier steps and artifacts remain inspectable after later failure.
- Refreshing the browser does not discard persisted progress.

## Scaling path

| Local MVP | Production equivalent |
| --- | --- |
| SQLite | Postgres |
| Local artifact directory | S3/R2 |
| In-process background task | Modal/container job |
| SQLite event polling | Redis Streams, Postgres LISTEN/NOTIFY, or queue |
| One API instance | Stateless autoscaled API |
| Local child process | Network-disabled sandbox |

The durable `run_id` and event contract are the key abstraction. The worker can move off-process while the REST and SSE interfaces remain stable.

## Tradeoffs to discuss

**Why application-owned history?** It gives deterministic persistence, exportability, and vendor independence. The model receives a bounded recent transcript, while tool traces remain in the application's audit log.

**Why not arbitrary database access from the browser?** The API enforces read-only access, result limits, lineage, and scientific defaults while keeping the dataset and credentials server-side.

**Why deterministic demo mode?** It makes the repository fully testable without sharing a secret and gives reviewers a reliable walkthrough. Setting an API key switches to flexible model-selected analyses using the same tools and UI.

**What would be evaluated next?** A golden set of scientific questions with expected tables, coverage checks, and numerical assertions; tool-selection accuracy; SQL validity; artifact correctness; latency; and scientist review of interpretation quality.
